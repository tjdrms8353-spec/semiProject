# 송성근 ONFIT 개발 시작 점검

점검일: 2026-10-22 (Asia/Seoul)

## 1. 결론과 점검 범위

현재 애플리케이션은 화면·API 골격과 샘플 응답을 갖춘 프로토타입이다. 실제 회원 인증, 프로필 저장, 인바디 추출, 찜 저장, 개인화 추천은 아직 구현되지 않았다. 확정 ERD는 **11개 테이블**, 현재 SQL 초안은 **9개 테이블**, SQLAlchemy 매핑 모델은 **0개**다. 따라서 현재 SQL을 그대로 실행하거나 Alembic 초기 마이그레이션으로 채택하면 안 된다.

이번에는 파일·Git·설정·패키지·문서의 읽기 전용 점검과 이 보고서 작성만 수행했다. 기능 코드, 공통 설정, DB 스키마, 다른 팀원 파일을 수정하지 않았다. 패키지 설치, TiDB 접속, SQL 실행, 마이그레이션, Git commit/push/merge, 배포는 수행하지 않았다.

사용자의 최신 지시와 루트의 `ONFIT_ERD_단일통합_가로형.pdf`를 기능·DB 기준으로 삼았다. 이전 Spring Boot·쇼핑몰 주문/발주 설계는 현 개발 기준으로 사용하지 않는다. 이하 API·파일 추가안은 **개발 계획이며 아직 구현되거나 합의된 계약이 아니다**.

## 4. TiDB 연결 및 SQLAlchemy·Alembic 상태

- `app/core/config.py`: Pydantic Settings가 환경변수와 **실행 작업 디렉터리 기준 `.env`**를 읽는다. `DATABASE_URL` 기본값은 빈 문자열이다. 프로젝트 루트 `.env.example`을 backend의 `.env`로 복사하도록 README에 안내되어 있다.
- 실제 `.env`/`.env.local` 파일은 검색되지 않았고, `.env.example` 두 개만 있다. 현재 프로세스에도 `DATABASE_URL`, `SECRET_KEY`, `APP_ENV`, `FRONTEND_ORIGINS`가 없었다. Render나 다른 팀원 환경의 값은 알 수 없다. 비밀값은 보고서에 기록하지 않는다.
- `.env.example`은 `mysql+pymysql`, 포트 `4000`, DB명 `onfit`, `ssl_verify_cert`·`ssl_verify_identity` 옵션을 가진 자리표시자다. 실제 계정·호스트가 아니다. CA 경로/신뢰 저장소, TLS 검증, URL 특수문자 인코딩은 실제 개발 DB에서 별도로 확인해야 한다. 인증서 검증을 끄는 방식으로 해결하지 않는다.
- `app/db/session.py`: 동기 `create_engine(..., pool_pre_ping=True)`, `DeclarativeBase`, `sessionmaker`, 세션 종료용 `get_db()`가 있다. URL이 없으면 engine/SessionLocal은 `None`이며 DB 사용 시 예외가 발생한다.
- 전체 backend 검색에서 `__tablename__`, 매핑 컬럼, relationship으로 선언된 ORM 모델을 찾지 못했다. `schemas/profile.py`, `schemas/product.py`는 **Pydantic DTO이며 DB 모델이 아니다**.
- 현재 라우터는 `Depends(get_db)`를 사용하지 않는다. 프로필 저장 응답은 입력을 되돌려줄 뿐 영속화하지 않는다.
- Alembic은 README만 있고 `alembic.ini`, `env.py`, `versions/`가 없다. metadata 연결·리비전·현재 DB 버전 모두 미확인이다.
- `database/schema.sql`은 실행 여부를 알 수 없는 **9개 테이블 초안**이며, `seed.sql`은 안내 주석뿐이다.

**실제 TiDB 원격 테이블과의 비교는 미실시다.** 연결 정보가 없는 상태에서 원격 DB가 비어 있다고 단정하지 않는다. 다음 단계에서 개발 전용 계정이 준비되면 읽기 전용으로 현재 database, 테이블/컬럼/인덱스/FK, Alembic 버전을 조회하고 확정 ERD와 다시 대조해야 한다. `CREATE TABLE`, `create_all`, `alembic upgrade`부터 실행하지 않는다.

## 5. 확정 11개 테이블과 현재 코드의 차이

기준: Git 루트 `ONFIT_ERD_단일통합_가로형.pdf`의 전체 텍스트와 FK/UK 표기. ERD는 컬럼명·관계 중심이며 자료형·길이·NULL·기본값·삭제 정책을 모두 명시한 DDL이 아니다. 아래의 “초안 추가 컬럼”은 ERD에 표시되지 않은 컬럼이라는 뜻이며, 임의 삭제 지시가 아니다. **SQLAlchemy 모델은 아래 11개 전부 미구현**이다.

| 확정 테이블 | 확정 ERD 컬럼 | 현재 schema.sql과 차이 |
| --- | --- | --- |
| `users` | `id`, `email`, `password_hash`, `name`, `created_at` | `password_hash` 없음. `name` 대신 `display_name`. 현재 email UNIQUE와 PK는 존재 |
| `user_profiles` | `id`, `user_id`, `height_cm`, `weight_kg`, `body_shape`, `preferred_fit`, `preferred_style`, `personal_color`, `preferred_colors` | `id` 없이 `user_id`가 PK. ERD는 `id` PK + `user_id` FK/UK. `weight_kg`, `personal_color`, `preferred_colors` 없음. `style_preference`, `fit_preference`, `favorite_color`는 확정명과 다름. 초안에 `updated_at` 추가 |
| `inbody_records` | `id`, `user_id`, `height_cm`, `weight_kg`, `skeletal_muscle_kg`, `body_fat_pct`, `measured_at`, `created_at` | 테이블 자체 없음 |
| `outfits` | `id`, `user_id`, `recommendation_type`, `explanation`, `estimated_total`, `created_at` | `recommendation_type`, `explanation`, `estimated_total` 없음. 초안에 `title`, `match_score` 추가 |
| `outfit_items` | `id`, `outfit_id`, `product_id`, `slot`, `price_snapshot` | `id`, `slot`, `price_snapshot` 없음. `(outfit_id, product_id)` 복합 PK로 되어 있어 ERD의 독립 `id` PK와 다름 |
| `favorites` | `id`, `user_id`, `product_id`, `created_at` | 테이블 자체 없음. `wardrobe_items`로 대체할 수 없음 |
| `products` | `id`, `brand`, `model_code`, `name`, `category`, `color`, `size`, `style_tags`, `image_url` | `model_number`, `product_name`으로 이름 불일치. `size`, `style_tags`, `image_url` 없음. 초안에 `created_at` 추가. 기존 인덱스도 `model_number` 기준 |
| `crawl_logs` | `id`, `job_type`, `status`, `collected_count`, `failed_count`, `started_at`, `finished_at` | `job_type`, `collected_count`, `failed_count` 없음. 초안에는 `source_name`, `items_seen`, `error_summary` |
| `sellers` | `id`, `name`, `website_url` | 테이블 자체 없음 |
| `product_offers` | `id`, `product_id`, `seller_id`, `source_item_key`, `product_url`, `current_price`, `availability`, `last_checked_at` | `seller_id` 및 sellers FK, `source_item_key`, `availability` 없음. `current_price_krw`로 이름 불일치. 초안에 `seller_name`, `option_label` 추가 |
| `price_histories` | `id`, `offer_id`, `price`, `collected_at` | `price_krw`, `observed_at`으로 이름 불일치. 초안에 `source_status` 추가 |

집합 비교: ERD 11개 중 현재 SQL과 이름이 같은 테이블 8개, 누락 3개(`inbody_records`, `favorites`, `sellers`), ERD 외 테이블 1개(`wardrobe_items`)다. 기존 데이터 유무를 모르므로 `wardrobe_items`를 삭제하거나 이름만 바꾸면 안 된다.

관계 기준:

- `users` → `user_profiles`: 선택적인 1:1, `user_id` FK/UK.
- `users` → `inbody_records`, `favorites`, `outfits`: 각각 1:N.
- `products` → `favorites`, `outfit_items`, `product_offers`: 각각 1:N.
- `outfits` → `outfit_items`: 1:N.
- `sellers` → `product_offers`: 1:N.
- `product_offers` → `price_histories`: 1:N.
- `crawl_logs`: 독립 테이블.

문서 충돌도 존재한다. 루트와 앱 내부의 `08_ERD_테이블_정의서.docx`는 Spring Boot 소유권·공급업체·주문·발주·트렌드 등 이전 12개 테이블을 설명한다. `프로젝트구조 및 기술스텍.pdf`는 현재 기술 스택을 설명하지만 DB 목록에는 이전 `wardrobe_items`가 남아 있다. 확정 ERD보다 이 문서나 현재 SQL을 우선하지 않는다.

### 개발 전 합의가 필요한 DB 세부 사항

1. 확정 **이름은 그대로 유지**하고 자료형, 길이, NULL, 기본값, 인덱스, FK 삭제 동작을 공동 DDL로 보완한다. 특히 금액 정밀도/통화, 신체 수치 단위, 시간대, `style_tags`·`preferred_colors`의 저장 형식이 필요하다.
2. `favorites(user_id, product_id)` 중복 방지 제약은 ERD에 명시되지 않았다. 중복 찜 API 동작과 함께 합의한다. 승인 없이 UNIQUE를 추가하지 않는다.
3. `outfit_items`의 독립 PK와 slot별 중복 허용 여부, 가격 스냅샷 기준 판매처·옵션을 정한다. `estimated_total`과 부분 가격 누락 처리도 맞춘다.
4. 인바디 ERD에는 원본 파일 경로·추출 상태·신뢰도 컬럼이 없다. 초기에는 추출 미리보기와 확인 요청을 분리하고 확정 수치만 저장하는 안을 검토한다. 파일/작업 상태 테이블이나 컬럼을 임의 추가하지 않는다.
5. 옷장은 `favorites`와 `products`로 구성한다. 현재 확정 ERD에는 별도의 개인 소장 의류/`is_owned` 구조가 없으므로 “찜”을 “실제 보유”로 표시하거나 별도 옷장 테이블을 만들지 않는다.

## 6. 현재 API와 프론트 연결 상태

전역 prefix는 `/api`이며 다음 7개 업무 경로와 `/health`가 소스에 등록되어 있다. 현재는 실사용 인증 계약이 없다.

| 현재 메서드·경로 | 실제 구현 상태 |
| --- | --- |
| `GET /api/auth/status` | prototype 안내 |
| `POST /api/profiles/` | 입력 검증 후 그대로 반환, 인증/저장 없음 |
| `POST /api/outfits/recommendations` | 고정 SAMPLE_OUTFITS 반환. 입력 시 설명만 일부 첨부; 개인화 순위 계산 아님 |
| `GET /api/wardrobe/` | 빈 items와 prototype 반환 |
| `GET /api/products/` | 샘플 상품 반환; 안종범 영역 |
| `GET /api/products/{product_id}/offers` | 빈 offers; 안종범 영역 |
| `GET /api/prices/{product_id}/insight` | 데모 분석; 이승호 영역 |
| `GET /health` | DB와 무관한 정적 상태 확인 |

위 업무 경로는 7개이며, `/health`를 포함하면 총 8개다. Swagger 등 프레임워크 기본 문서 경로는 별도다.

프론트 확인 결과:

- `AuthModal.jsx`: 제출 시 안내 문구만 표시한다. 실제 가입/로그인 요청 없음. 비밀번호 길이 UI와 서버 정책을 함께 합의해야 한다.
- `StyleProfilePage.jsx`: 스타일·색상을 React 상태로 보관하고 저장 버튼은 완료 표시만 변경한다. 선호 핏은 아직 API 입력으로 연결되지 않았다.
- `OutfitPage.jsx`, `WardrobePage.jsx`: 정적 코디/상품을 사용한다.
- `services/api.js`: 추천 fetch helper가 있으나 현재 화면에서 사용되는 호출을 발견하지 못했다. 오류 시 mockProducts를 반환해 추천 코디 응답과 상품 응답의 형태가 달라질 수 있다.
- 현재 입력은 `style`, `favorite_color`, `fit_preference`지만 확정 DB는 `preferred_style`, `preferred_colors`, `preferred_fit`이다. DTO 매핑 또는 API 입력 전환을 황상옥과 합의한다. 선호 색상을 `personal_color` 진단 결과로 임의 취급하지 않는다.
- 샘플 ID는 `p1`, `look-01` 등 문자열이다. 실제 SQL 초안은 숫자 PK이므로 실제 ERD 자료형 확정 후 API ID 직렬화 규칙을 정한다. 큰 정수의 JavaScript 정밀도도 고려한다.
- 샘플 점수 96·92, Unsplash 이미지, 데모 가격은 실제 추천 정확도·수집 실적이 아니다. `run_once.py`, `worker.py`도 외부 수집 없이 로그만 남기는 골격이다.

## 7. 송성근 담당 API 계약 초안

공통안: `/api` prefix 유지, JSON snake_case, 개인 데이터는 인증된 사용자에서 `user_id`를 결정한다. URL/본문의 임의 `user_id`를 신뢰하지 않는다. 사용자 응답에서 `password_hash`는 제외한다. 아래 `/me` 경로와 응답 형식은 프론트 합의 후 적용하며 기존 경로를 무단 삭제하지 않는다.

| 순서 | 메서드·경로 제안 | 요청·응답 및 수용 기준 |
| --- | --- | --- |
| 1 | `POST /api/auth/signup` | `email`, `password`, `name` → 201 사용자 공개 정보. 이메일 중복 409, 입력 오류 422. 저장은 password_hash |
| 1 | `POST /api/auth/login` | JSON email/password → 200 access_token·token_type·expires_in. 실패 401, 존재 여부를 과도하게 노출하지 않음 |
| 1 | `GET /api/auth/me` | Bearer 인증 → 본인 id/email/name. 만료·변조·미인증 401 |
| 2 | `GET /api/profiles/me` | 본인 프로필 조회, 선택 생성 전 상태는 404로 문서화하는 안 |
| 2 | `PUT /api/profiles/me` | 전체 프로필 생성/교체. `height_cm`, `weight_kg`, `body_shape`, `preferred_fit`, `preferred_style`, `personal_color`, `preferred_colors`. 신규 201/수정 200 규칙 명세 |
| 2 | `PATCH /api/profiles/me` | 부분 수정. 필드 미제공과 명시적 null 구분, 검증 실패 422 |
| 3 | `POST /api/profiles/me/inbody/extract` | multipart PDF/이미지 → 추출 수치·원문 근거·확인 필요 항목 미리보기. 이 단계는 DB 기록 생성 안 함. 용량 413, 형식 415, 파싱 오류 422 등 |
| 3 | `POST /api/profiles/me/inbody-records` | 사용자가 확인한 측정값과 measured_at → 201 본인 인바디 기록. created_at은 서버 처리 |
| 3 | `GET /api/profiles/me/inbody-records` | 본인 기록 페이지 조회. measured_at 기준 순서·페이지 규약 명시 |
| 3 | `DELETE /api/profiles/me/inbody-records/{record_id}` | 본인 기록만 삭제, 204/404. 타인 ID도 노출하지 않음 |
| 4 | `GET /api/wardrobe/` | 기존 경로 유지. 본인 favorites + products 목록, 페이지 규약·sample 표시 합의 |
| 4 | `POST /api/wardrobe/favorites` | `product_id` → 201 찜. 없는 상품 404. 중복 시 기존 결과 200 또는 409 중 하나를 계약으로 확정 |
| 4 | `DELETE /api/wardrobe/favorites/{favorite_id}` | 본인 찜만 삭제, 204/404 |
| 5 | `POST /api/outfits/recommendations` | 기존 경로 유지. 프로필 기반 또는 찜 기반 recommendation_type 선택. outfits·outfit_items 원자적 저장 및 설명·slot·가격 스냅샷 반환 계획 |
| 5 | `GET /api/outfits/` | 본인 저장 추천 목록 |
| 5 | `GET /api/outfits/{outfit_id}` | 본인 코디와 구성 상품 조회, 타인 코디 404 |

개인화 API는 Bearer 인증을 제안한다. JSON 로그인과 Swagger의 Authorize 동작은 HTTP Bearer 방식으로 맞추는 안이며, OAuth2 form 로그인 방식으로 바꿀 경우 프론트와 입력 타입을 다시 합의한다. refresh/logout/토큰 폐기 저장소는 이번 필수 범위에 자동 추가하지 않는다. 토큰 수명·브라우저 보관 방식은 프론트와 결정한다.

Swagger 작성 계획: 명시적인 Pydantic 요청/응답 모델, `response_model`, 성공 상태 코드, tags, summary, description, 인증 scheme, 오류 응답 예시를 각 경로에 선언한다. 업로드 MIME/크기/실패 응답, 개인 데이터 소유권, null/단위/시간대, 샘플 구분, 페이지네이션을 `/openapi.json`에 표현한다. 프론트에 OpenAPI 계약과 요청 예시를 제공한 뒤 구현한다. 지금은 이 표가 계약 초안이며 Swagger 구현 완료로 간주하지 않는다.

추천 데이터가 부족하면 이유와 빈 결과를 반환하고 점수를 만들어 채우지 않는다. 개발용 샘플은 명시적 모드와 응답 표식으로 구분한다. 인바디 추출은 텍스트 PDF를 먼저 처리하고 이미지·스캔은 OCR 결과를 사용자 확인 후 반영한다. 추출 오류를 0으로 저장하지 않으며 인바디 수치를 의료 진단이나 퍼스널컬러 확정값으로 해석하지 않는다.

## 9. 공통 파일 변경 이유·영향 및 충돌 주의사항

| 공유 지점 | 필요한 이유 | 영향 및 협업 방법 |
| --- | --- | --- |
| ORM Base·모델 import | 11테이블 관계와 FK 구성 | 각자 Base를 만들면 metadata가 분리됨. 등록 위치·모델 소유자·import 순환 방지를 먼저 합의 |

| users·인증 dependency | 모든 개인 데이터의 주체 결정 | 프론트 로그인과 개인 API 모두 영향. 서버에서 identity 결정, 본인 데이터만 조회/갱신 |
| `app/main.py` | 필요 시 공통 오류 처리·앱 lifecycle | 전역 영향. 현재 라우터가 이미 등록되어 있어 본인 4개 모듈 내부 개발만으로는 변경 불필요. 필요가 생기면 사전 영향 설명 |

| 가격 스냅샷 | estimated_total/price_snapshot | 이승호와 최신가격 시간·통화·품절·유효성 합의. 가격이력 미수집을 실제 분석처럼 표시하지 않음 |
| frontend DTO | 현재 style/favorite_color/fit_preference와 확정명 불일치 | 황상옥과 전환 일정 및 하위 호환 여부 결정. 기존 `/api` prefix·슬래시·mock fallback의 타입 차이 확인 |
| render.yaml·CI 위치 | 실제 Git 루트와 설정 경로 불일치 | 배포 담당 포함 공동 검토. 이번에는 배포·워크플로 실행/수정 없음 |
| 문서 기준 | 구 DOCX, 구조 PDF, SQL 사이 설계 차이 | 최신 11개 ERD와 사용자 지시를 기준으로 변경 목록 관리. 기존 문서 일괄 덮어쓰기 금지 |

추가 운영 원칙: 개발 DB와 실사용 DB 분리, 환경변수·로그·예외 응답에 비밀번호/토큰/원본 인바디 노출 금지, 개발용 기본 SECRET_KEY를 production에서 허용하지 않는 검증 필요. 업로드는 허용 형식·크기·임시 파일명·삭제 시점·접근 권한을 정하고 비동기 작업 저장이 필요해지면 별도 설계 검토한다. 동기 SQLAlchemy 세션을 async 경로에 무조건 직접 호출하지 않도록 실행 모델도 통일한다.

현재 코드가 미추적 상태라 `git diff`가 비어 있어도 앱 변경이 없다는 뜻은 아니다. 다른 팀원의 로컬 파일을 보호하고 전체 디렉터리 재생성, `git add .`, checkout/reset 등으로 작업 상태를 바꾸지 않는다. 별도 요청 없이 commit/push/merge/배포하지 않는다.

**우선 구현할 첫 기능은 회원가입·로그인·내 정보다.** 다만 선행 작업은 `users`의 확정 컬럼(`id`, `email`, `password_hash`, `name`, `created_at`)을 기준으로 현재 SQL의 차이와 자료형/제약을 합의하고, 실제 개발 DB 및 Python 실행 환경을 확인하는 것이다. 비밀번호 컬럼이 없는 초안 위에 인증부터 붙이지 않는다.

첫 개발 작업의 제안 범위는 users 모델, auth 요청/응답, 해시·토큰 모듈, `get_current_user`, auth 라우터, 인증 테스트다. 완료 판정은 가입 후 로그인/내 정보 조회, 중복 이메일 409, 잘못된 비밀번호·만료/변조 토큰 401, 비밀번호 해시 비노출이며 테스트용 DB에서 검증한다. 모델·Alembic·의존성·설정 변경은 9절의 이유와 영향을 팀에 공유한 뒤 진행한다.

## 11. 점검 근거와 남은 확인

검사: `git status`, branch/HEAD/추적 참조 비교, 전체 파일·디렉터리 목록, Python 직접 경로 실행 및 importlib.metadata, Python 30개 AST 분석, 라우터·설정·DDL·프론트 연결 코드 읽기. ERD 및 구조 PDF는 압축 스트림과 ToUnicode 매핑의 전체 텍스트를 읽었고, 이전 DOCX는 OOXML 텍스트를 읽어 비교했다. PDF의 시각적 배치 품질은 이번 코드 점검 대상이 아니다.
